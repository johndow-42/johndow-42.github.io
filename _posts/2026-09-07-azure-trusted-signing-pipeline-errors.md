# Why Your Azure Trusted Signing Pipeline Breaks (and the Real Fixes)

If you maintain a Windows build pipeline, you've probably noticed two things happening at once this year: your code-signing certificates are expiring faster than they used to, and more teams around you are moving signing into Azure Trusted Signing (recently renamed Azure Artifact Signing). Neither of these is a coincidence, and neither of them is going smoothly. This post walks through why, with the exact error messages you'll hit, links to the real GitHub issues behind them, and what's actually fixed versus what you still have to work around yourself.

## The 460-day cliff is not a rumor

On November 17, 2025, the CA/Browser Forum passed **Ballot CSC-31**, cutting the maximum validity of publicly trusted code-signing certificates from 39 months down to **460 days** (about 15 months), effective for every certificate issued **on or after March 1, 2026**. That date has already passed as of this writing — if you bought a certificate this year, it's on the new clock. Multiple certificate authorities confirm the same numbers independently: [DigiCert's own explainer](https://www.digicert.com/blog/understanding-the-new-code-signing-certificate-validity-change) states it plainly, and the timeline lines up with the broader industry trend of shrinking certificate lifetimes (the same forum has TLS certificates heading toward 47 days by 2029).

Practically, this kills the "buy a 3-year cert, drop it in a build server, forget about it" pattern a lot of Windows shops have run for a decade. You're now renewing, re-provisioning, and re-testing your signing step roughly twice as often. That math is exactly why cloud-managed signing services — Azure Trusted Signing chief among them — have gotten a lot more attractive this year: Microsoft holds the key material and handles certificate rotation, so your pipeline doesn't need a human to notice a `.pfx` is about to expire. That's the pitch, anyway. What actually happens when teams migrate is messier.

## What breaks when you actually wire it up

`electron-builder` is one of the most widely used tools for shipping signed Windows apps out of GitHub Actions, and its Azure Trusted Signing integration has generated a steady stream of real, reproducible failures. Three worth knowing by their exact symptoms, because you'll likely hit one of them if you search your own error text:

- **[#8828](https://github.com/electron-userland/electron-builder/issues/8828)** — the PowerShell install step fails first with `No match was found for the specified search criteria for the provider 'NuGet'.`, and if you push past that, the actual signing call comes back with a **403 Forbidden** from the Azure Trusted Signing service. This is closed now, but it's a good illustration of how many separate things have to line up (PowerShell provider bootstrap, then real Azure auth) before signing even starts.
- **[#8948](https://github.com/electron-userland/electron-builder/issues/8948)** — building an APPX for the Microsoft Store, electron-builder tries to sign the final package artifact even though Microsoft re-signs Store submissions itself, and that redundant signing call fails with `SignTool Error: An unexpected internal error has occurred.` (403 again). There's also a genuinely confusing detail here: the `publisherName` option has to be passed as `CN=<company name>`, not just `<company name>`, despite what the docs imply — closed via PR #9335.
- **[#9076](https://github.com/electron-userland/electron-builder/issues/9076)** — signing multiple binaries concurrently in the same build causes file-lock errors like `The process cannot access the file...Azure.CodeSigning.Dlib.dll because it is being used by another process`, because the Trusted Signing toolchain isn't safe to initialize from parallel processes. Closed via PR #9454.

The pattern across all three: Azure Trusted Signing's client tooling is young, and the integration layer between it and popular build tools has had real, user-blocking bugs — not vague "flakiness," but specific, reproducible error strings you can grep your build logs for. If you're hitting any of these, check what electron-builder version you're on relative to the fixing PRs before you spend hours debugging your own config.

## If you're not using electron-builder, you're not off the hook

Plenty of teams call [`Azure/artifact-signing-action`](https://github.com/Azure/artifact-signing-action) directly from their own GitHub Actions workflow instead of going through electron-builder. I went looking at this layer specifically — the module install/cache step that runs before any actual signing happens — and found three confirmed, still-open bugs in the official action as of this writing:

- **[#146](https://github.com/Azure/artifact-signing-action/issues/146)** — a user running x64 and arm64 jobs in the same matrix hit a cached-module conflict on arm64. Worth being precise here: the maintainer's first response was that arm64 isn't officially supported by the underlying signing tools at all, not that this is a confirmed caching bug — they later softened that to "multiple reports of caching inconsistencies" worth investigating. Treat this one as a real, reported problem with an unresolved root cause, not a confirmed cache-key bug.
- **[#155](https://github.com/Azure/artifact-signing-action/issues/155)** — not a `-Repository PSGallery` flag as you might assume from the action's inputs. The `TrustedSigning` PowerShell module itself has a hardcoded NuGet endpoint inside `NugetInstall.psm1` (`$location = "https://www.nuget.org/api/v2/"`), with no parameter exposed to override it. If your org blocks direct nuget.org access, there's currently no supported way around this at the action layer.
- **[#141](https://github.com/Azure/artifact-signing-action/issues/141)** — this one is worse than "fails silently": the post-job `actions/cache` save step exits non-zero *after* signing has already completed successfully, and that failure **does** fail the overall workflow run — the reporter's own words: "workflow runs that produce verified-signed releases still show ❌ on the Actions tab." Your artifact is correctly signed, but CI shows red, which is exactly the kind of noise that trains a team to stop trusting its own red X's.

This one I can speak to first-hand, because I built and shipped a fix for the first two: [`setup-artifact-signing`](https://github.com/johndow-42/setup-artifact-signing) is a small composite action you run before `Azure/artifact-signing-action` that scopes the cache key by `RUNNER_ARCH` (so x64 and arm64 jobs never collide) and exposes a `repository` input so you can point it at your own pre-registered `PSRepository`. It doesn't sign anything itself — that's still the official action's job — it just makes sure the module install step underneath it is reliable. I verified both fixes in CI on real free GitHub-hosted runners, `windows-latest` and `windows-11-arm`, including a genuine cache-hit-on-second-run check and a real custom-repository install path, not just unit tests against mocked inputs.

The #141 bug is worth being honest about instead of overselling a fix: a composite action has no hook into `actions/cache`'s post-job step, so there's structurally no way to detect or suppress that save-step failure from the outside — that's a GitHub Actions platform limitation, not something a wrapper action can close. What `setup-artifact-signing` does instead is log the cache key and hit/miss status on every run, so when you see that red X on an otherwise-successful signing run, your own logs already tell you it's the known post-job cache save failure and not a real signing problem, instead of you having to rediscover that from scratch. If a signing job you know succeeded is still showing red, check that output before you start debugging the signing step itself.

## If the signing step lives inside a Jenkins pipeline instead

Not everyone is on GitHub Actions. If your signing step is a stage in a declarative Jenkinsfile, the equivalent failure mode is different but the underlying lesson — "the official tool has one specific, documented edge case that breaks a workflow you'd never think to check" — repeats. The official offline validator, `jenkinsfile-runner`, ships a `lint` command, but invoking it with a custom command drops its default `-w`/`-p` flags. That makes it fall back to downloading a fresh Jenkins WAR over HTTPS at container startup, and on the `latest` image tag (last published in 2022, no newer tag exists), that download fails with an SSL handshake error because the embedded Java runtime's CA trust store is outdated ([jenkinsfile-runner#738](https://github.com/jenkinsci/jenkinsfile-runner/issues/738)). I ran into this building [`jflint`](https://github.com/johndow-42/jflint), a one-command offline Jenkinsfile linter — it always points `-w`/`-p` back at the WAR already bundled in the image, so linting stays fully offline and never triggers that download at all. If you want to catch a broken `parallel`/`agent` combination or similar declarative-pipeline mistakes before you push and wait on a real Jenkins server, `npm install -g jenkinsfile-lint` gets you the `jflint` command; it's a thin, honest wrapper, not a reimplementation of Jenkins' own validation engine.

## What to actually do about it

1. **Check your certificate's issue date against March 1, 2026.** If it was issued after that date, it's capped at 460 days — put an expiry reminder on it now, not when the build starts failing.
2. **If you're on electron-builder with Azure Trusted Signing, make sure you're on a version at or after PR #9335 and #9454** before you burn time debugging `publisherName` formatting or file-lock errors that are already fixed upstream.
3. **If you call `Azure/artifact-signing-action` directly**, either scope your own cache key by `RUNNER_ARCH` and register a mirror `PSRepository` yourself, or drop in `setup-artifact-signing` and get both for free, plus visible cache-key/cache-hit logging so a silent `actions/cache` save failure doesn't stay invisible.
4. **Don't assume a green build today means a green build in 460 days.** Cert rotation is now a recurring pipeline event, not a one-time setup step — treat it like a dependency update, with monitoring, not tribal knowledge.

None of this required guessing. Every error string above is quoted from a real, linked GitHub issue, and the two fixes I describe as "shipped" are shipped — tested in CI on real free-tier Windows runners, both x64 and arm64, with the honest limitations (the actual `Invoke-ArtifactSigning` call itself, and the `actions/cache` post-step bug) documented rather than hand-waved away.
